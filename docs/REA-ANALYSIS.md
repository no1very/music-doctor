# REA 式分析与功能复刻记录

本项目使用 [REA（Reverse Engineer Anything）](https://github.com/morluto/rea) 的方法论来拆解
[Music Tag Web](https://github.com/xhongc/music-tag-web)，并在**不接触其商业版代码**的前提下重建功能。

本文记录：分析了什么、证据来自哪里、哪些结论是高置信的、哪些是推断，以及最终如何映射到实现。

---

## 1. 方法论：REA 的工作方式

REA 是一个「用 Agent 逆向任何东西」的工具链：通过 MCP 服务把**目标取证**（进程、二进制、网络、
前端资源、数据库）暴露给智能体，智能体基于证据回答行为问题，再把行为模型写成可验证的实现。

其核心循环可以抽象为：

```
观察目标 → 形成行为假设 → 取证（截图/请求/二进制/文档）→ 修正假设 → 实现 → 回归验证
```

对**有源码**的目标，REA 用静态分析 + 运行观察；对**闭源/商业**目标，则依赖运行观察与公开文档。
本项目属于后者，因此把「取证」阶段落在公开资料上，并明确标注推断部分。

### 本次执行环境的限制（已记录以保证可复现）

| 限制 | 影响 | 应对 |
| --- | --- | --- |
| Shell 无法访问外网（仅 HTTP 工具可访问白名单域名） | 无法拉取 V2 镜像、无法 `npm i` REA | 通过文档站点与 GitHub API 取证 |
| 无第三方 Python 包、无 Node 依赖安装 | 不能用 FastAPI/Django/mutagen | 标准库实现 HTTP、SQLite、ID3/FLAC 解析 |
| Chromium 受沙箱 IPC 限制无法启动 | 不能对 V2 做浏览器自动化截图 | 用文档截图与教程文本作为 UI 证据 |
| V2 为闭源商业版（需激活码） | 无法对二进制做动态分析 | **不做**二进制逆向、**不做**授权绕过 |

> 结论：这不是一次「二进制级」逆向，而是**证据驱动的行为重建**。
> 所有推断都在第 6 节标明置信度。

## 4. 行为模型（从证据推导）

### 4.1 领域对象

由 E1/E3/E4 的表述可推出最小领域模型：

```
媒体库(Library/目录) → 曲目(Track/文件) → 专辑(Album) → 艺术家(Artist)
                    ↘ 标签源(TagSource/插件)  → 候选(Candidate) → 写入
                    ↘ 任务(Task) → 进度/日志
                    ↘ 歌单(Playlist: 静态 | 智能规则)
                    ↘ 用户(User: 角色) → 收藏 / 播放队列 / 播放历史
                    ↘ 房间(Room) → 成员 / 同步状态
```

关键推断：V2 的「智能歌单」是**查询而非快照**（E3 说「根据满足条件快速从音乐库中创建」「持续按条件更新」），
因此实现为每次读取时求值，而不是定时物化。

### 4.2 标签流水线

```
扫描目录 → 读取容器标签/音频参数 → 入库(SQLite) → 候选搜索(多源) → 评分 → 写回文件 + 封面/歌词 → 版本快照
```

- 「写回文件」是 V2 与纯播放器的根本差异（E1「可编辑歌曲标题、专辑、艺术家、歌词、专辑封面等完整音频元数据」）。
- 「元数据版本管理」意味着每次写入前后都要可比较、可回退 → 需要快照表（E1）。
- 「异步任务中心」意味着扫描/刮削/批处理必须脱离请求生命周期 → 需要任务表 + 工作线程（E1）。

### 4.3 变量模板（E2 给出了精确规范）

- 仅解析 `${...}`，不支持 Mako 块语法；
- 变量名固定（`title`/`artist`/`albumartist`/`tracknumber`/…）；
- 支持 Python 表达式：`zfill`、`strip`、`replace`、`split`、条件表达式、`or` 兜底；
- 明确列出**不支持**的写法（`$if(...)` 等）。

这是全部证据中规范最完整的一处，因此实现完全对齐，并额外做了 **AST 白名单**以满足安全要求。

### 4.4 播放与多端

E1 列出：收藏、播放记录、Subsonic 兼容、跨设备队列/曲目/进度同步、多端同播房间。
推断：
- 跨设备同步需要一个以用户为键的队列快照（曲目 id 列表 + 当前位置 + 毫秒进度）；
- 多端同播需要「房间 + 状态广播」，且要避免回声（应用远端状态时不能再上报）。

实现上用 SSE 广播房间状态，并在客户端加 `applyingRoom` 抑制回环。

### 4.5 UI 信息架构（由 E1 功能清单推断）

```
仪表盘 | 音乐库 | 专辑 | 艺术家 | 歌单 | 任务中心 | 去重 | 一起听 | 设置
播放器底栏（封面/标题/进度/队列/音量）
```
V2 截图无法获取，因此视觉风格为原创（深色 + 青绿主色），**不复制**其视觉设计。

## 7. 刻意排除：授权与激活

V2 通过激活码解锁（E1）。复刻它需要：

1. 逆向上游的激活协议；
2. 伪造/绕过授权校验；
3. 分发其闭源产物或密钥。

这三件事都可能违反许可与法律，也违背 REA 的合法使用边界（REA 明确要求只分析「你拥有或获授权
检查的软件」）。因此本项目：

- **不实现**任何激活码、试用期、机器码或许可证校验；
- **不包含** V2 的任何代码/资源/密钥；
- **不提供**任何绕过手段；
- 若你需要商业版能力与支持，请购买正版授权。

## 10. 第二轮：授权确认后的增补

第二轮开始时，项目所有者确认已购买授权，但出于隐私无法提供实例（激活后入口隐藏，上游也已停止更新）。
因此**取证条件没有变化**：仍然没有二进制、没有前端 bundle、没有私有 API 样本。
第 6 节的置信度表继续有效。

这一轮按公开文档补齐了此前标为缺失的能力，全部依据公开规范实现：

| --- | --- | --- | --- |
| MCP / Agent 接入 | E1「插件模块 / Agent 配置 / MCP」+ MCP 公开规范 | `app/mcp.py`（JSON-RPC + 11 工具） | e2e 7 项（initialize/tools/list/tools/call/鉴权/撤销） |
